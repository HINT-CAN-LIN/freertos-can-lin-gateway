1. 팀원 5 분 요약 
 한 줄 결론 
Gateway 는 통신/시 스 템 Fault 를 감지·관리·전 파 하 고, 실제 안 전 출 력 은 해당 
ECU 가 직접 수 행 합 니 다. Gateway 가 Motor 에 Fail-safe 명 령 을 내 려 야 만 
안 전 해 지 는 중앙집중 구조는 사용하지 않습니다. 
 
항목 현재 결론 상태 
책임 분리 Gateway = 시스템 Health/Fault 관리·전파 / 각 ECU = 실제 Fail-safe 출력·기능 Recovery 확정 
VCU Timeout VCU_Command 10 ms expected, age > 30 ms → VCU_TIMEOUT  Handbook 
Motor 안전동작 Motor 가 VCU_Command 를 직접 감시, Fault 시 TorqueApplied=0 / target_rpm=0, RPM 은 0 으로 수렴 확정 
Fault State NORMAL / DEGRADED / FAIL_SAFE /  OFFLINE 4 개만 사용 확정 
Recovery 통신 Fault 는 정상 조건 3 회 연속 확인 후 복구 팀 결정 
Queue Drop QUEUE_DROP 자체는 DEGRADED, drop 횟수만으로 FAIL_SAFE 전환하지 않음 확정 
다중 Fault 각 Fault 를 ACTIVE/CLEARED 로 독립 관리, 대표 State 는 FAIL_SAFE > OFFLINE > DEGRADED > 
NORMAL 
확정 
표시 정책 Cluster = 대표 상태 + 주요 Fault / PC Tool = 모든 Active Fault + 상세 로그 확정 
Gateway SW HealthTask 가 감시, FaultManager C 모 듈 이 Fault 상태/복구/우선순위 관리 확정 
Critical Timeout 30 ms VCU Timeout 을 100 ms Health 주 기 에 만 의존하지 않고 deadline/event 경로로 즉시 처리 확정 
UDS MVP 에는 미 포 함, M4/M5 이후 여유가 있 으 면 Stretch Goal 로 재검토 잠정 결정 
 
 가장 자주 헷갈린 부분 
대표 System State는 Motor 를 멈추게 하는 명 령 이 아 닙 니 다. Motor 의 
Fail-safe 는 Motor 가 직접 수 행 합 니 다. 대표 System State 는 Gateway 가 
전체 Fault 심 각 도 를 요약해 Cluster/PC 에서 활 용 하 기 위한 상 태 입 니 다.

2.2 D-07 이 해결해야 하는 질문 
질문 이번 설 계 에 서 정한 방향 
누가 Fault 를 감 지 하 는 가? Gateway 가 시 스 템/통신 Health 를 감 지 하 며, 안 전 이 필 요 한 ECU 도 필 요 한 입 력 을 직접 감 시 합 니 다. 
누가 Fail-safe 를 실 행 하 는 가? 실제 안 전 출 력 은 해당 ECU 가 직접 수 행 합 니 다. 
Fault 가 여러 개면? 모든 Fault 를 독립 보 존 하 고 대표 System State 만 Severity 로 요 약 합 니 다. 
언제 정 상 으 로 복 구 하 는 가? 통신 Fault 는 정상 조건 3 회 연속 확인 후 복 구 합 니 다. 
어 떻 게 외부에 알 리 는 가? Fault_Status 를 이용해 Cluster/PC 에 전 파 하 는 구조를 유 지 합 니 다. 
30 ms Timeout 을 어 떻 게 제때 찾는가? 일반 Health 주 기 와 별 도 로 Critical deadline/event 감시 경 로 를 사 용 합 니 다. 
 
 D-07 완료의 의미 
Fault Detection 만 구 현 하 면 완료가 아닙니다. 감지 기준 → 상태 전이 → 
Fail-safe → 외부 전파 → Recovery 까지 하나의 흐름으로 검 증 되 어 야 
합 니 다.

5. Recovery 와 다중 Fault 관리 
5.1 Recovery 기본 정책 [확정] 
 핵심 원칙 
정상 Frame 1 개가 들 어 왔 다 고 즉시 정 상 복 귀 하 지 않습니다. 통신 Fault 는 
정상 조건을 연속 확인한 뒤 복 구 합 니 다. 
 
Fault 복구 조건 근거/상태 
VCU_TIMEOUT 정상 VCU_Command + Valid + Alive 를 3 회 연속 확인 3 회 = 팀 결정 
DOOR_ECU_OFFLINE 정상 Door Response + Alive 를 3 회 연속 확인 
Detection 3-cycle 은 Handbook / 
Recovery 3 회는 팀 결정 
ALIVE_ERROR 정상 Alive sequence 를 3 회 연속 확인 3 회 = 팀 결정 
QUEUE_DROP Queue Full 해소 + 추가 Drop 없음 + Queue Health 정상화 3-frame 규칙 미적용, 정량 정상화 기준 미확정 
 
5.2 다중 Fault 독립 관리 [확정] 
Active Fault Table 
VCU_TIMEOUT       ACTIVE    → FAIL_SAFE  
DOOR_OFFLINE      ACTIVE    → OFFLINE  
QUEUE_DROP        ACTIVE    → DEGRADED  
ALIVE_ERROR       CLEARED   → - 
 
Representative System State = 가장 높은 Severity = FAIL_SAFE 
 
상황 대표 System State 
VCU_TIMEOUT + DOOR_OFFLINE + QUEUE_DROP 모두 ACTIVE FAIL_SAFE 
VCU_TIMEOUT 만 복구, DOOR_OFFLINE + QUEUE_DROP ACTIVE  OFFLINE 
Door 도 복구, QUEUE_DROP 만 ACTIVE DEGRADED 
모든 Fault CLEARED NORMAL 
 
 대표 State 의 역할 
대표 System State는 ECU Fail-safe 명령이 아니라 “현재 시스템 전체 
심 각 도 요약”입 니 다. 실제 Fail-safe 는 각 ECU 가 자기 Fault 기 준 으 로 독립 
수 행 합 니 다.

 실제 Fail-safe 출력은 Motor 등 해당 ECU 가 직접 수 행 하 므 로 Gateway에 “FailSafeTask”를 하나 더 둘 필요성이 낮습니다. 
 Fault 정책은 FaultManager 모듈로 분리하면 별도 Task/Queue/동기화 복잡도를 추 가 하 지 않고 테 스 트 할 수 있 습 니 다. 
 Gateway 의 역할은 system health 판단·상태 관리·전파이며, ECU local action의 실행 컨 텍 스 트 를 대 신 하 지 않 습 니 다.

 발견된 설계 충돌 
Handbook 예 시 에 서 는 Health 100 ms Task 주 기 를 제 시 하 지 만, 
VCU_TIMEOUT 기 준 은 age > 30 ms 입 니 다. HealthTask 가 100 
ms 마다 polling 만 하면 30 ms Fault 를 늦게 검 출 할 수 있습니다.

       │ 
       └─ Critical deadline 감시 갱신 
                    │ 
             30 ms 초과 Event 
                    │ 
                    ▼ 
            HealthTask 즉시 Wake-up 
                    │ 
             실제 age 재 확 인 
                    │ 
                    ▼ 
               FaultManager 
                    │ 
               VCU_TIMEOUT 
 
 D07-8 결정 
일반 Health 감 시 는 기존 HealthTask 가 담당하되, Health 기본 주 기 보 다

8. QUEUE_DROP 처리 정책 
8.1 Queue Drop 이 무엇인가? 
CAN Frame 수신 
    ↓ 
CAN HW FIFO / RX Interrupt  
    ↓ 
CAN ISR 
    ↓ xQueueSend 실패 (Queue Full) 
CANRxQueue  ───────► CANRxTask  
 
→ HW 에서 Frame 을 받 았 더 라 도 SW Queue 가 Full 이면 상위 처리 전에 Frame 이 유실될 수 있음 
 
 CAN Hardware FIFO 와 FreeRTOS Queue는 서로 다른 계 층 입 니 다. 
 ISR 은 최소 작업만 수 행 하 고 Queue 로 Task 에 넘 기 는 것이 Handbook 기본 구 조 입 니 다. 
 Queue Drop 이 반복되면 특정 Message 의 Alive 누락/age 증가가 발생해 2 차 Fault 로 이 어 질 수 있 습 니 다. 
근거: Handbook 8.1~8.3, 10.1 
8.2 D07 Queue 정책 [확정] 
 결정문 
QUEUE_DROP 자 체 는 DEGRADED 로 관리합니다. Drop 횟수만을 
기 준 으 로 별도 FAIL_SAFE 임 계 값 을 두지 않 습 니 다. 반복 Drop 때문에 
Critical Message Timeout/Alive Error가 발생하면 “그 2 차 Fault”의 
State 로 전 이 합 니 다. 
 
상황 처리 
Queue 1 회 Full / Drop QUEUE_DROP ACTIVE → DEGRADED  
Drop 반복, 하지만 Critical Timeout 없음 DEGRADED 유지 + log/KPI 
Drop 영향으로 VCU_Command age > 30 ms VCU_TIMEOUT 발생 → FAIL_SAFE 
Queue 가 정상화됨 추가 Drop 없음 + Queue Health 정 상 화 후 QUEUE_DROP 
Recovery 
 
 미결정 
Queue Health “정 상 화”의 정량 기준(예: occupancy %, no-drop 
duration)은 아직 만들지 않 았 습 니 다. 임의 수 치 를 넣지 않고 실제 Queue 
depth/부하 설계와 함께 Gateway SW Architecture에서 Freeze 합니다.

9. UDS / MVP / Stretch Goal 판단 
9.1 개념 정리 
용어 프 로 젝 트 에 서 의 의미 
MVP 
이 프로젝트가 성공했다고 말할 수 있는 최소 필수 완성 범위. CAN/LIN Routing, Fault/Fail-safe/Recovery, PC Tool, Test 가

UDS

9.2 Gateway 진 단 과 UDS 진단의 차이 
구분 Gateway Fault/Health 판단 UDS 를 붙인 PC 진단

예 VCU_TIMEOUT, ALIVE_ERROR, Door Offline 판단 “저장된 Fault 정보 읽기” 같은 요청/응답 
필수성 MVP 핵심 MVP 필수 아님 
관계 Fault 를 만들어/저장하는 쪽 이미 판단된 정보를 읽거나 진단 동작을 요청하는 쪽 
 
9.3 장단점과 현재 판단 
장점 단점 
자동차 진단 구조 경 험 을 포트폴리오에 추가 가능 요청/응답, ECU Handler, Test 범위가 새로 늘어남
