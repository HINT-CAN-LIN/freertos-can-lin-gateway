현재 확정된 Architecture
항목
현재 기준
Gateway 역할
CAN Node + LIN Master. CAN/LIN Signal Routing, Schedule, System/Network Health, Fault State 관리와 Cluster/PC 전파를 담당한다.
CAN 수신 경계
CAN RX ISR은 Raw CAN Frame을 CANRxQueue로 전달하는 최소 작업만 수행한다. 검증, Decode, Cache 갱신은 CANRxTask가 수행한다.
LIN 경계
LINSchedulerTask/LIN Master가 10 ms slot, 100 ms supercycle의 Schedule을 실행하고 Header/Response 경계를 소유한다.
Signal Cache
같은 수신 Frame의 원시 입력값과 실제 수신시각을 함께 보존하고, validity 및 그룹 Health와 일관된 Snapshot으로 Routing/Health에 제공한다. LIN
cache writer Task, 필드 표현과 동기화 방식은 TBD이다.
Routing 경계
Routing Manager가 Cache Snapshot을 읽고 Routing 조건과 변환을 평가한다. 실제 CAN/LIN Bus 송신은 CAN Interface 또는 LIN Master가
담당한다.
Health/Fault
HealthTask가 정상 Health polling과 Critical VCU deadline/event 경로를 담당하고, FaultManager가 Fault별 ACTIVE/CLEARED, Recovery,
Representative SystemState를 관리한다.
Local Fail-safe
Gateway가 모든 ECU의 안전 출력을 직접 수행하지 않는다. Motor/Window 등 영향 ECU가 Local Fail-safe를 수행한다. Gateway는 상태 관리와
외부 전파를 담당한다.
외부 전파
Gateway_Status 0x300 cyclic, Vehicle_Status.NetworkState 0x120 cyclic, Fault_Status 0x310 event를 통해 Cluster/PC Tool에 전파한다.
Logger
ISR에서 직접 printf 하지 않는다. Health/Fault/Event를 Queue 기반으로 LoggerTask에 전달한다.
TBD / Open
●
Task priority, stack size, Queue depth, item size, 정확한 RTOS API와 대부분의 Task period는 현재 기준 문서에서 확정되지 않았다.
●
HealthTask의 일반 Health polling 100 ms와 VCU 30 ms Critical deadline/event 경로는 확인되지만, Timer/Task Notification/EventGroup 등 구체 API는 TBD이다.
●
Signal Cache의 timestamp/age 타입·time base·snapshot 보호 방식, LIN 수신 cache writer Task, 최종 validity 결합/API는 TBD이다. CAN 수신시각과 Cache 반영시각은 구분하며, Queue
대기시간이 source age에서 사라지지 않게 해야 한다.
●
Light_Status와 Motor_Status의 timeout 정량값은 정의되지 않았다. Door의 3-cycle 또는 Window의 2-cycle을 임의로 복사하지 않는다.
●
CAN Tx request path, LIN Tx request queue의 depth와 overflow policy는 TBD이다.
●
Fault_Status 다중 Fault Event의 송신 순서, 재전송, 유실 시 Cluster/PC 동기화 정책은 TBD이다.
●
신규 Body Command 입력은 Routing Table v1.0에서 VCU_Command Byte3 bit 24-31 후보로 정의되었으나 IFC-02~06의 DBC/Matrix 반영과 상대 검토 전까지 공식 Interface로 취급하지
않는다. 기존 Gear/Brake route도 Gear 범위와 Brake invalid 표기의 DBC/정의서 동기화가 남아 있다.

Interface가 Gateway 내부 어떤 Module과 RTOS 경계를 통과하는지만 고정한다.

보고서에서는 다음과 같이 기존 Module 내부 책임으로 배치한다.

5.2 CANRxTask 책임 경계
●
ISR에서 Decode, Routing, Fault policy, printf를 수행하지 않는다.
●
CAN ID와 DLC 검증은 CANRxTask에서 수행한다.
●
Signal bit layout, scaling, enum은 02 FIX 및 그에 동기화된 DBC를 참조한다.
●
유효하지 않은 Signal 또는 Message는 Cache에 정상값으로 기록하지 않는다.
●
VCU_Command는 Routing 입력이면서 Health/Fault 입력이다. age > 30 ms 판단은 Gateway Health/Fault 경로에 포함되며 Motor Local Monitoring과 독립이다.
●
Motor_Status, Gateway_Status의 Alive는 Message별 정책에 따라 검사한다. Alive 불연속은 ALIVE_ERROR 입력이 된다.

9.4 Critical deadline path
The 30 ms VCU timeout cannot depend only on a nominal 100 ms HealthTask polling period. The architecture therefore has two HealthTask entry paths.
VCU_Command received
  -> update VCU Cache age/alive
  -> arm/update critical deadline observation
VCU deadline exceeds 30 ms
  -> deadline/event signal
  -> HealthTask wake-up
  -> actual age re-check
  -> FaultManager VCU_TIMEOUT
The concrete software timer, task notification, event group, or equivalent mechanism is TBD. The deadline path must not be replaced by a 100 ms-only poll.
9.5 Fault event and propagation
●
Each Fault ACTIVE <-> CLEARED transition generates one Fault_Status event according to 02/05.
●
One event represents one Fault transition. Simultaneous transitions require multiple events.
●
Fault_Status fields are FaultCode, ECUOffline, RecoveryState, SystemState according to 02/05 FIX.
●
Gateway_Status is cyclic and currently contains GatewayAlive and QueueUsage; do not add GatewayHealth or SystemState without Interface Change review.
●
Event ordering, retransmission, lost event recovery, and Cluster/PC Active Fault Table resynchronization are Open decisions.

CANRxQueue는 ISR -> CANRxTask 단일 방향으로 소유한다.
●
Signal Cache는 Queue가 아니라 Module API와 Snapshot 경계로 취급한다.
●
EventQueue를 여러 Consumer가 직접 경쟁 소비하는 구조는 피한다. Fault propagation과 Logger가 같은 Event를 모두 받아야 하면 fan-out 또는 별도 Queue를 결정해야 한다.
●
Queue depth, item size, high-water 기준, drop recovery는 구현/시험 전 Freeze해야 한다. 현재 수치는 임의로 만들지 않는다.

15.3 구현 원칙
●

●
Gateway는 Motor/Window의 Local Fail-safe 출력을 직접 제어하지 않는다. Gateway는 관련 상태를 감시하고 CAN/PC/Cluster로 전파한다.
●
CAN/LIN Interface 변경은 Routing Table, DBC/LDF, Firmware, PC Tool, Test의 동시 검토를 요구한다.
●
모든 [초기값 - 수정 가능] 값은 코드 주석과 Configuration 문서에 PROPOSED_REVIEW로 표시한다.

17.3 Frame 단위 Snapshot 및 수신 이벤트
●
DoorOpen과 DoorLocked는 같은 Door_Status Frame 그룹에서 읽는다. DoorStatus와 별도 DoorOpen 출력을 같은 CAN Body_Status payload 평가 때 같은 Snapshot으로 계산한다.
●
LampState는 LightStatus와 bit-4 기반 ReverseLamp 출력에 공통으로 사용한다. 두 값은 동일 Light_Status Snapshot에서 산출한다.
●
WindowState와 같은 Window Frame의 Alive/상태정보도 Frame 단위 일관성을 갖는다. 서로 다른 Frame 수신을 하나의 원자적 snapshot으로 가정하지 않는다.
●
새 Frame마다 Alive를 한 번 평가한다. Cache를 반복 읽은 횟수로 Alive 오류·복구 카운트를 증가시키지 않는다. 빠른 연속 Frame에서 최신 Cache 덮어쓰기 전 필요한 평가 결과를 전달할
RX/Health 이벤트 경로는 TBD이다.
●
읽기 중 일관성 보호 방법, Snapshot 수명, retry/실패 처리와 LIN RX cache writer Task는 미정이다. 이를 FreeRTOS Task 설계 단계에서 확정한다.

18.3 Queue Sizing 방법
각 Queue의 최종 Depth는 다음 기준으로 산정한다.
Depth >= 최대 Service Blocking 시간 동안의 Peak Arrival + Burst Margin + Recovery Margin
측정 기록에는 Frame Arrival Rate, 최대 Task Blocking 시간, Queue High-water Mark, Drop Count, Test Duration을 포함한다. 위 초기값은 첫 번째 Sizing 후보일 뿐이다. SYS_REQ_053의
Queue Recovery는 QueueUsage 80% 미만, 신규 Drop 없음, HealthTask 3회 평가를 요구한다.
18.4 Static Allocation과 RTOS Object 규칙

printf, Heap Allocation, Bounded되지 않은 Loop를 사용하지 않는다. ISR Queue 전송은 FromISR API를 사용하며 필요한 경우에만 Context Switch를 요청한다. Static/Dynamic 선택은 [검토

19. CAN RX 상세설계
19.1 처리 순서
1
CAN Peripheral이 Frame을 수신하고 최소 ISR Callback을 호출한다.
2
ISR은 Bounded Raw Frame을 CanRxFrame_t에 복사하고 Timestamp를 기록한 뒤 CANRxQueue에 Enqueue한다.
3
Queue가 가득 차면 ISR은 Drop Counter를 증가시키고 Deferred Queue Health Event를 설정한다. ISR이 SystemState를 직접 변경하지 않는다.
4
CANRxTask가 Channel, ID, DLC, 예상 Message Format을 검증한다.

5

6

CAN에 Routing하지 않는다.

[미정]이다.
21. Routing 상세설계
21.1 Route 평가 알고리즘
각 Route는 다음 순서로 평가한다.
1
Route Table Version과 Route Enable 조건을 확인한다.
2
Signal Cache에서 일관된 Source Snapshot을 읽는다.
3
Source Entry validity와 같은 Frame Group의 rx_stamp, received state, Alive/age/offline Health를 일관된 Snapshot으로 확인한다. Route 사용 시점에 age를 다시 계산한다.
4
Route Condition을 적용한다. Invalid 또는 Stale한 Critical Source로 정상 Destination 값을 만들지 않는다.
5
승인된 Signal Definition에 따라 Conversion, Range, Clamp를 적용한다.
6
Destination Command Shadow 또는 Status Aggregation Object를 갱신한다.
7
소유 Bus Interface를 통해 Bounded CAN 또는 LIN Request를 제출한다.
8
진단을 위해 Route 결과, Source Generation, Destination, Reject Reason을 기록한다.
위 알고리즘은 Architecture의 Route 실행 계약이다. 구체 행은 첨부 Routing Table v1.0을 반영했으며, 해당 표가 Review/OPEN이거나 DBC/LDF/Matrix 동기화가 필요한 항목은 검토 상태를
그대로 유지한다.

22.2 HealthTask Wake 경로
HealthTask는 두 가지 논리적 Wake 경로를 가진다.
●

Polling만으로는 SYS_REQ_055를 만족하지 못한다.
