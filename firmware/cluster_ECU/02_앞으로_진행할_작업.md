# Cluster ECU 앞으로 진행할 작업

작성일: 2026-10-11

기준: 로컬 `firmware/cluster_ECU`의 현재 코드, `CLUSTER_REVIEW_FIXES.md`, `CLUSTER_RTOS_TASKS.md`, `CLUSTER_CAN_LOOPBACK.md`, 2026-10-11 문서 대조 리뷰. 시스템 문서 검토 기준은 develop 커밋 `226e88e076171037d9e115e9722ec3cbdc18e268`이며, 그 이후 모든 원격 문서 변경을 재검토했다는 의미는 아니다.

## 우선순위

다음 핵심 단계는 CANable을 사용한 외부 CAN 수신 시험이다. DMA·터치 추가보다 실제 입력, 유실 진단, 통합 시나리오와 재현 가능한 증거 확보를 먼저 진행한다.

## 1. 현재 상태 보존과 IOC 재생성 확인

- 현재 수정 코드와 문서를 commit하고, 팀 절차에 따라 push/PR을 진행한다.
- `.settings`는 환경별 값이 달라질 수 있다. Debug 산출물과 환경 설정의 추적 정책은 팀과 합의한다. 임의 전체 삭제/Discard를 하지 않는다.
- 원본을 보존한 별도 복사본에서 IOC Generate Code → diff → build → boot를 확인한다.
- CAN Mode/핀 Pull-up, SPI pin/NSS/clock, TIM6 timebase, IRQ priority 5, 두 Task/stack, USER CODE body가 유지되는지 확인한다.
- 성공 기준: 태스크 중복 생성·사용자 함수 유실 없음, build 통과, startup selftests 및 Uptime 정상.

## 2. 외부 CAN RX 모드로 전환

`Core/Inc/cluster_state.h`:

```c
#define CLUSTER_CAN_LOOPBACK 0
#define CLUSTER_TEST_INPUT 0
```

IOC의 CAN1 Mode를 **Normal**로 변경하고 재생성한다. `Core/Src/can.c`의 `hcan1.Init.Mode=CAN_MODE_NORMAL`을 확인한 뒤 build/download한다. 자동 테스트 데이터가 사라지고 외부 입력만 반영되어야 한다.

CAN1 RX PA11/TX PA12는 트랜시버의 RXD/TXD에 연결한다. CANable과는 트랜시버 CANH/CANL, 공통 GND로 연결한다. PA11/PA12를 CANH/CANL에 직접 연결하지 않는다. 트랜시버 전원과 logic level, 두 끝의 종단 구성을 확인한다.

버스 속도는 500 kbps로 맞춘다. 내부 루프백 성공은 외부 결선·ACK·종단 성공을 보장하지 않는다. 생산 Cluster의 애플리케이션 TX는 계속 없다.

## 3. CANable 기본 수신 및 DBC 시험

| 시험 | 확인할 결과 |
|---|---|
| 6개 ID 정상 Standard DATA/DLC8 | 캡처 값과 화면 표시·수신 시각 일치 |
| 미등록 ID, EXT, RTR, 잘못된 DLC | 필터 또는 decoder 거부; 정상 값/time을 오염시키지 않음 |
| Speed/RPM/torque min/max/초과/FFFF | 배율과 invalid 표시 일치 |
| Gear 0..7, Brake 0/1, Door, Window enum | 승인 value table대로 표시 |
| Light 각 bit, 63, 64, FF | 63은 전체 ON; reserved/invalid 처리 확인 |
| Alive wrap/중복/jump/restart | sequence 검사 결과 및 표시 정책 확인 |
| Fault ACTIVE/중복/두 개/한 개 CLEARED/NONE | 남은 Fault 유지, 임의 reset 금지 |
| cyclic 중단/재개 | 현재 임시 1초 stale/3초 offline 및 회복 확인 |
| Vehicle missing/stale + 새 Fault | 최근 Fault 대표 상태 표시; 숫자 freshness는 별도 |

프레임 파일, 사용 DBC 버전/hash, CAN 캡처, 펌웨어 commit, 사진/영상, 기대값·실측값을 시험별로 저장한다. UI fake 입력 테스트와 외부 CAN 테스트를 같은 증거로 처리하지 않는다.

## 4. 정상 부하 및 과부하 계측

현재 cyclic 주기 기준 10/10/20/100/100 ms는 약 270 frames/s이며 Fault Event는 별도다. 이 조건으로 먼저 시험한다. burst/과부하는 별도 시험으로 구분한다.

관측 변수:

- `cluster_can_rx_count`, `cluster_can_rx_drops`, `cluster_can_error`, `cluster_can_current_errors`
- `cluster_can_rx_queue_max` 및 queue current
- `cluster_ui_status`, `display_status`, `stack_overflow_task`
- `ui_stack_free_words`, `can_stack_free_words` × 4 = free bytes
- `cluster_heap_free_bytes`, 모델 rejected frame 수

추가 계측이 필요한 항목: RX→모델→화면 지연, queue 대기시간, mutex hold/wait, 각 Task 최장 실행/중단 시간. 수신 시각 보존만으로 end-to-end 표시 지연을 측정했다고 판정하지 않는다.

정상 정의 부하에서는 loss 0과 양 Task 진행을 확인한다. 과부하에서는 loss/uncertainty 진단과 지속 실행을 확인한다. 장시간 운전의 목표 시간·부하·합격 지연은 팀과 먼저 정한다. 합격 기준이 정해지지 않은 수치를 PASS로 포장하지 않는다.

`QUEUE:85%`는 Gateway가 보낸/test 생성한 지표이며 Cluster의 RX queue 점유율이 아니다. 로컬 queue 판단은 `RXQ:n/64`, queue_max/drop으로 한다.

## 5. 통신 및 표시 오류 시험

- CAN initialization failure: INIT ERROR와 진단 상태 확인.
- 통제된 bus-off, disconnect/reconnect: current error와 history 분리 및 ABOM 이후 실제 수신 재개 확인.
- RX FIFO overrun/queue overflow: drop 집계 및 Fault 테이블 불확실 표시 확인.
- SPI 초기/런타임 실패: UI 상태 반환과 LED 등 별도 관측 확인.
- Fault Event 유실/순서 변경/Cluster reset: 현재 동기화 한계를 기록한다. 계약 확정 전 완전 복구 PASS로 판정하지 않는다.

## 6. 팀 설계 결정 반영

[설계 공백 문서](03_설계_공백_및_팀_결정.md)의 D1~D5를 Gateway/PC/Test/문서 담당과 확정한다. 결정 후 Cluster 표시 정책·시험 기대값을 수정한다. 승인 없는 DBC 신호나 Cluster Fault TX를 독자 추가하지 않는다.

## 7. Gateway 통합 및 완료 증거

Vehicle/GearR/ReverseLamp, Door lock/open, VCU timeout, Door/Window offline, multi-fault, CLEARED recovery를 실제 Gateway와 시험한다. 관련 SCN-01/03/04/05/06/07/08/09/10은 현행 시나리오 문서의 절차·기대값을 적용한다.

Gateway detection → CAN event/status → Cluster LCD를 같은 시간축으로 기록한다. 노드 자체 fail-safe는 해당 ECU 책임이며 Cluster는 수신 결과를 표시한다.

최종 완료 조건:

- [ ] 승인 DBC/요구사항과 구현·표시 정책 정합화
- [ ] IOC 재생성 회귀시험 통과
- [ ] 외부 CAN 6개 ID·경계값·필터 시험 통과
- [ ] 정상 부하 loss 0 및 합의된 표시 지연/메모리 여유 충족
- [ ] 오류/복구/장시간 시험 통과
- [ ] Fault 동기화 제한의 해결 또는 팀 승인된 제한 명시
- [ ] Gateway 통합 증거 및 Jira/PR 추적 연결
- [ ] Debug/Release build 및 image fit 확인

## 8. 필요할 때만 추가하는 기능

SPI DMA는 CPU 대기/표시 지연 계측 결과로 필요성을 판단한다. 적용 시 완료 thread flag 또는 semaphore 하나와 timeout/abort/CS/DC/buffer lifetime 처리를 함께 구현한다. DMA는 SPI wire time 자체를 줄이지 않는다.

Touch(XPT2046), SD, 추가 Cluster TX는 현재 검토한 필수 요구가 아니다. 요구 승인과 메모리 예산 없이 추가하지 않는다. 현재 Flash 잔여 약 19.7 KB이므로 기능 추가 전 크기를 다시 측정한다.
