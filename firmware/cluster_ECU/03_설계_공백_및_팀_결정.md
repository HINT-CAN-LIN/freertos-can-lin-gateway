# Cluster ECU 설계 공백 및 팀 결정 사항

작성일: 2026-10-11

기준: 로컬 `firmware/cluster_ECU`의 현재 코드, `CLUSTER_REVIEW_FIXES.md`, `CLUSTER_RTOS_TASKS.md`, `CLUSTER_CAN_LOOPBACK.md`, 2026-10-11 문서 대조 리뷰. 시스템 문서 검토 기준은 develop 커밋 `226e88e076171037d9e115e9722ec3cbdc18e268`이며, 그 이후 모든 원격 문서 변경을 재검토했다는 의미는 아니다.

## 범위

이 문서는 코드에서 확정적으로 수정할 오류와 팀 계약이 필요한 공백을 구분한다. SystemState 선택, snapshot 시각 순서, Fault redraw, 로컬 CAN 진단의 기존 오류는 수정 완료됐다. 아래 미결 사항은 Cluster 코드만 독자 수정해서 해결했다고 판정할 수 없다.

## D1. Event-only Fault 테이블 동기화 — 우선 결정

**공백:** ACTIVE/CLEARED 이벤트만으로는 Cluster 부팅 전 Fault, 유실된 이벤트, 오래된 이벤트의 역순 도착, Gateway 재시작을 완전 복원할 수 없다. 현재 DBC에는 sequence/epoch/snapshot 계약이 없다. 기존 Gateway DD-007 및 aligned RTOS D-10도 재시도/순서/재동기화를 OPEN으로 둔다.

**현재 처리:** code+node 멱등 테이블, 해당 CLEARED만 해제, 수신 gap/loss 시 불확실 표시. `gap_seen`은 자동 해제하지 않는다. 최근 Gateway cyclic 수신만으로 Fault 테이블 전체 정확성을 보장하지 않는다. Fault Event 하나만 조용히 유실되면 현재 인터페이스로 검출하지 못할 수 있다.

**결정할 질문:**

- 부팅/재접속 때 현재 ACTIVE 전체를 어떻게 알려주는가?
- ACTIVE/CLEARED 순서와 재전송을 어느 계층이 보장하는가?
- Gateway 재시작 또는 generation 변경을 어떻게 구분하는가?
- 테이블 불확실 상태를 어떤 증거로 해제하는가?
- 인터페이스를 유지한다면 어떤 known limitation을 운영 정책으로 승인하는가?

**담당 협의:** Gateway + Cluster + PC Tool + Test + 인터페이스 담당.

**승인 후 작업:** replay/snapshot/sequence 등 선택한 계약을 관련 문서·DBC·펌웨어·PC Tool·시험에 함께 반영한다. CAN 계약 변경은 기존 SYS_REQ_058 변경 절차(Jira → 메시지/요구 문서 → 상대 리뷰 → DBC → FW/Tool/Test → Evidence)를 따른다.

**피해야 할 임시 해결:** 일정 시간 뒤 Fault 자동 삭제, NONE을 reset-all로 사용, Cluster가 근거 없는 Gateway Fault_Status를 생성.

## D2. 채널별 stale/offline 기준

**공백:** 현재 모든 cyclic channel의 1000/3000 ms는 임시 표시 정책이다. 최신 검토 문서가 이 숫자를 최종 동결하지 않았다.

**결정:** 채널의 10/20/100 ms 주기, jitter와 버스/Task 지연, UI 허용 지연을 반영해 stale/offline threshold 및 복구 조건을 정한다. 이벤트 SystemState freshness/last-known/UNKNOWN 정책도 함께 확정한다.

**책임 구분:** Gateway의 VCU 30 ms 또는 LIN Door/Window cycle timeout을 Cluster의 CAN channel timeout으로 그대로 복사하지 않는다. Body 프레임이 fresh여도 개별 노드는 offline일 수 있다.

**담당:** 시스템/요구사항 + Gateway + Cluster + Test.

**검증:** threshold ±1 ms, pause/recovery, delayed frame, HAL tick wrap, gateway absent, cyclic/event 선후 관계.

## D3. Health·노드 상태·대표 Fault의 의미

**공백:** 최근 프레임 수신, Alive 연속성, signal validity, source ECU offline, 로컬 CAN 오류가 모두 다른 의미다. 현재 RX 채널 OK를 ECU 전체 정상으로 읽을 수 있다.

**현재:** channel freshness와 Fault/invalid를 일부 구분하고 local CAN current/history를 별도 표시한다. Alive sequence 검사 결과가 모든 UI Health 라벨에 직접 반영되지는 않는다. Light offline overlay의 최종 매핑/표현은 승인 범위 확인이 필요하다.

**결정:**

- 채널 OK를 “최근 프레임 수신”으로 명확히 표기할 것인가?
- Alive duplicate/jump/restart를 화면에 어떻게 표현하고 회복시킬 것인가?
- Door/Light/Window offline과 FF invalid/reserved를 어떻게 구분할 것인가?
- major Fault 선정 순서와 미관측 Fault/UNKNOWN 표현을 승인할 것인가?

대표 Fault 요구가 곧 전체 Fault 목록 UI 요구는 아니다. 목록·터치 페이지를 필수 기능으로 확대하지 않는다.

**담당:** 시스템/Cluster + 관련 ECU + Test.

## D4. 운용·성능·오류 회복 기준

**설계 선택:** UI 초기화 성공 후 CAN Task 시작. LCD 초기화 실패 시 CAN 초기화도 진행되지 않는다. 화면 장애에도 통신을 독립 유지해야 한다면 시작 장벽과 초기화 책임 분리가 필요하다.

**미결 목표:** UI 표시 지연, worst-case queue 점유/Task 지연, stack/heap 최소 여유, 장시간 시험 기간, local RX loss 후 운용, LCD 실패 후 재시도/중단 및 별도 진단 경로.

**확인된 것:** 태스크 분리와 내부 loopback 저부하 실행은 통과했다. 따라서 “태스크 분리 미구현”은 현재 공백이 아니다.

**아직 시험할 것:** 외부 CAN 정상 부하/burst, bus-off/ABOM recovery, 장시간 메모리, IOC regeneration, Debug/Release. 이는 구현 공백과 구분한 검증 공백이다.

**DMA 결정:** blocking SPI는 현재 설계다. queue 85%라는 Gateway 지표만으로 DMA 필수 판정하지 않는다. CPU/표시 지연 실측과 목표를 비교해서 결정한다.

**담당:** Cluster + 시스템 + Test.

## D5. 문서 및 DBC 정합화

| 항목 | 현재 코드 기준 | 필요한 정리 |
|---|---|---|
| Gear | 0..3 정상, 4..6 reserved, 7 invalid | 구 문서 범위를 최신 DBC/팀 결정과 정합화 |
| Brake | 0/1 정상 | 1을 invalid로 해석하는 구 설명 수정 |
| Alive | 0..15 wrap | invalid 표기와 sequence/restart 정책 구분 |
| Window raw 6 | RESERVED | numeric range 0..5와 value table 설명 정합화 |
| 신규 VCU request 5개 | 승인 DBC 전 비활성 | Routing 결정만으로 Cluster decoder 추가 금지 |
| 구 Fault layout/TBD | 최신 DBC 배치로 구현 | 이미 해결된 layout 문제와 D1 event transport OPEN 구분 |
| 구 Gateway RTOS 설계 | Cluster task 수를 정하지 않음 | Gateway 전용 책임과 Cluster 구현 구분 |

**담당:** 문서/DBC owner + 관련 ECU + Test. 현재 구현을 옛 문서에 맞춰 되돌리기보다 승인된 최신 인터페이스를 먼저 명시한다.

## 결정 상태 추적표

| 항목 | 현재 상태 | 승인/완료 증거 |
|---|---|---|
| D1 Fault 동기화 | OPEN | 계약 문서, 필요 시 DBC 변경, 부팅·유실·역순 시험 |
| D2 freshness 수치 | 임시 정책 | 채널별 기준과 경계 시험 |
| D3 Health UI | 일부 구현 / 최종 정책 미결 | 용어·노드 매핑과 UI 기대값 승인 |
| D4 성능·장애 운용 | 구조 구현 / 목표·통합 검증 미결 | 합격 기준 및 실측 결과 |
| D5 문서 정합화 | 최신 DBC 기반 구현 / 문서 정리 필요 | 일관된 승인 문서·DBC 버전 |

Touch/SD 미사용과 생산 Cluster 애플리케이션 TX 없음은 현재 필수 요구 누락으로 판정하지 않는다. 요구가 추가되면 별도 scope로 승인한다.
